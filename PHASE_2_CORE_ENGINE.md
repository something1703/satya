## 3. Defining "Manipulation" — The Conceptual Foundation

Before anything is coded, agree on what the model is asked to detect. Otherwise the team builds five different things.

SATYA detects three distinct categories of content problems:

**Category 1 — Synthetic generation:** the content was generated by AI. Deepfake video, AI-generated images, voice cloning, fully synthetic news article.

**Category 2 — Manipulation of authentic content:** real content edited to mislead. Doctored screenshots, video with swapped audio, image with cropped context, quote taken out of context.

**Category 3 — Misleading framing:** content is technically accurate but framed dishonestly. Old footage labelled as current events, statistics stripped of context, satirical content presented as real news.

The verdict schema (next section) captures all three categories with separate confidence scores. This nuance matters — calling everything "fake" is a one-bit answer and loses user trust the first time it's wrong.

## 4. The Verdict Schema — Locked Contract

This is the single most important artifact in Phase 2. Every team member uses it. Once locked, it does not change without a team-wide vote.

Save this as `mobile/lib/analysis/verdict_schema.dart` and as `ml/verdict_schema.json` (same shape, different language). Versioning starts at `v1`.

The verdict is a single JSON object:

```json
{
  "schema_version": "v1",
  "analyzed_at": "2026-05-09T14:32:11Z",
  "content_summary": "Short one-line description of what the content shows",
  "categories": {
    "synthetic_generation": {
      "confidence": 0.91,
      "evidence": [
        {
          "type": "facial_inconsistency",
          "location": "0:14",
          "description": "Lip movement does not match phoneme audio between 0:14 and 0:18"
        }
      ]
    },
    "authentic_manipulation": {
      "confidence": 0.12,
      "evidence": []
    },
    "misleading_framing": {
      "confidence": 0.08,
      "evidence": []
    }
  },
  "overall_verdict": "LIKELY_SYNTHETIC",
  "overall_confidence": 0.91,
  "recommendation": "DO_NOT_FORWARD",
  "explanation_short": "Two-sentence plain-language summary of why this verdict was reached",
  "explanation_detailed": "Longer paragraph for users who tap 'tell me more'"
}
```

**Enum values that must not drift:**

- `overall_verdict`: `LIKELY_AUTHENTIC` | `INCONCLUSIVE` | `LIKELY_MANIPULATED` | `LIKELY_SYNTHETIC`
- `recommendation`: `SAFE_TO_FORWARD` | `VERIFY_BEFORE_FORWARDING` | `DO_NOT_FORWARD`
- `evidence.type`: open vocabulary but the team maintains a glossary in `docs/EVIDENCE_TYPES.md`

This schema is enforced via Gemma 4's function calling — the model is given the schema as a tool definition and constrained to produce only outputs matching it. Free-form text is never trusted to be parseable.

## 5. Track A — The Analysis Engine

### 5.1 — How a single analysis flows

Plain English walkthrough of what happens when a user shares a video into the app:

1. App receives the file URI from Android's share intent
2. App computes SHA-256 hash of the file
3. App queries the verdict cache: "any existing verdicts for this hash?" (Phase 3 logic — for now, always cache miss)
4. App copies the file to a temp working directory
5. **Pre-processing:** the multimodal pipeline runs:
   - If video → extract 8 evenly-spaced frames via `ffmpeg_kit_flutter`
   - If video or audio → extract audio waveform as WAV
   - If image → use directly
   - If text/forwarded message → use directly
6. **Inference:** Gemma 4 E4B receives the multimodal payload along with a structured prompt + the verdict schema as a function definition
7. Gemma 4 reasons through the content (thinking mode visible in dev builds, hidden in prod) and emits a function call matching the schema
8. App parses the JSON, validates it against the schema (reject and retry if invalid)
9. App displays the verdict on the verdict screen
10. (Phase 3) App signs the verdict and publishes to cache

The agent codes each step as a method in `analysis/multimodal_pipeline.dart`, returning `Future<Verdict>` from a single `analyze(File content)` entry point.

### 5.2 — Prompt engineering for the verdict

The system prompt is doing real work. It must:

- State the model's role unambiguously ("You are a forensic media analyst")
- List what counts as evidence of each category (give 3–5 concrete examples per category)
- Instruct the model to be cautious — uncertainty is preferable to a confident wrong answer
- Force structured output via the function definition (not via plain text)
- Be in English even for non-English content (the model reasons in English then translates the `explanation_short` and `explanation_detailed` into the user's UI language)

The agent maintains a versioned prompt file at `mobile/lib/analysis/prompts/v1_system.md` so changes are tracked.

Key prompt-engineering rules learned from past hackathons:

- Never ask "is this fake?" — ask "what specific manipulation indicators do you observe?"
- Always require evidence before allowing high confidence
- Give the model an explicit `INCONCLUSIVE` escape hatch — hallucinated verdicts on ambiguous content are worse than honest uncertainty
- Cap evidence list at 5 items — longer lists are usually padded

### 5.3 — Function calling enforcement

`flutter_gemma` supports tool/function calling natively in recent versions. The agent registers `submit_verdict` as the only tool available to the model, with its parameter schema mirroring Section 4's JSON shape exactly.

If the model tries to respond in free text instead of calling the function, the pipeline rejects and re-prompts with: *"You must call the submit_verdict function. Free-text responses are not accepted."* Up to 3 retries, then return `INCONCLUSIVE` as a safe default.

### 5.4 — Multimodal handling: the practical details

**Video:** extract exactly 8 frames at evenly-spaced intervals (not keyframes — keyframes can be gamed). Resize each to 768×768 (Gemma 4's preferred vision input size). Encode as base64 PNG. Pass all 8 frames in a single inference along with the audio waveform.

**Audio:** down-sample to 16kHz mono WAV. Trim to 30 seconds max (longer clips slow inference dramatically and Gemma 4's audio context window has limits). For longer content, sample three 10-second windows: beginning, middle, end.

**Image:** resize to 768×768, encode as base64 PNG.

**Text:** clean whitespace, no other preprocessing. If the text references a URL, do NOT fetch it (would require internet and break the offline guarantee). Note the URL in evidence and ask the user to verify it separately.

**Forwarded message screenshots:** treat as image, but the model is prompted to read text via its built-in vision OCR rather than running a separate OCR step. This is a clean demonstration of Gemma 4's multimodal advantage.

### 5.5 — Performance budget

Target latencies on a Pixel 7 or equivalent mid-range device:

| Step | Target | Acceptable max |
|---|---|---|
| Frame extraction | 1.5s | 3s |
| Audio extraction | 1s | 2s |
| Hashing | <0.5s | 1s |
| Inference (full multimodal) | 6s | 15s |
| Schema validation + retry | <0.5s | 2s |
| **Total** | **~10s** | **~25s** |

If inference exceeds 25 seconds consistently, profile. Likely causes: GPU backend not engaged, frame count too high, audio clip too long.

### 5.6 — Dev logging

During development, every analysis writes a JSON log to the device at `/Android/data/com.satya/files/analysis_logs/<timestamp>.json` containing:

- Input file path and hash
- Frame extraction timing
- Full prompt sent to model
- Full raw model output
- Parsed verdict
- Total latency

These logs are inspected during the demo video shoot to find the most compelling examples. Strip this in production builds.

## 6. Track B — Fine-Tuning With Unsloth

### 6.1 — The dataset problem

This is the most-skipped step in hackathons and the difference between a project that benchmarks well and one that doesn't. Allocate one full day to dataset curation.

**Sources to draw from (all publicly available, all hackathon-legal):**

| Source | URL/Notes | What it provides |
|---|---|---|
| FakeAVCeleb | Public deepfake video dataset | Video deepfakes with ground truth labels |
| FaceForensics++ | Public face manipulation dataset | Manipulation type labels |
| LIAR dataset | Politifact-derived text claims | Misinformation text with veracity labels |
| MultiFC | Multi-source fact-check dataset | Fact-check verdicts in structured form |
| ASVspoof 2021 | Audio deepfake dataset | Synthetic vs real audio |
| Snopes / PolitiFact / FactCheck.org | Public archives | Real-world misinformation examples |
| Boom Live, Alt News (Indian context) | Public fact-check articles | Regional misinformation patterns critical for our demo |

**Don't only use Western datasets.** Add at least 200 examples from Indian/Asian/African fact-checks. Generalization across regions is what makes this app actually useful and is what judges will notice.

### 6.2 — Dataset format for instruction tuning

Convert all sources into a unified instruction-tuning format:

```json
{
  "messages": [
    {"role": "system", "content": "<system prompt from Section 5.2>"},
    {"role": "user", "content": "<multimodal content reference + metadata>"},
    {"role": "assistant", "content": "<function call: submit_verdict with full schema-conformant output>"}
  ]
}
```

Target dataset size: **8,000–12,000 examples**. Below 5,000 is too small for meaningful improvement; above 15,000 hits diminishing returns within Kaggle's GPU time limits.

Split: 85% train, 10% validation, 5% held-out test. The test set is sacred — never look at it during training, only at final evaluation.

### 6.3 — Unsloth training script

In the Kaggle notebook from Phase 1, add a fine-tuning cell. The agent writes this in `ml/unsloth_finetune.ipynb`. Conceptually:

- Load base Gemma 4 E4B with 4-bit quantization (already done in Phase 1)
- Apply LoRA configuration: rank 16, alpha 32, dropout 0.05, target modules: all attention + MLP projections
- Use `SFTTrainer` from `trl` with the formatted dataset
- Training config:
  - Learning rate: 2e-4
  - Batch size: 2 (Kaggle GPU memory limit)
  - Gradient accumulation: 8 (effective batch size 16)
  - Epochs: 3
  - Warmup ratio: 0.05
  - Save checkpoint every 500 steps
- Run training. On Kaggle's T4 x2, this takes roughly 6–10 hours for 10k examples.

### 6.4 — Evaluation — non-negotiable

After training, run evaluation on the held-out test set. Compute:

- **Accuracy** by category (synthetic generation, authentic manipulation, misleading framing)
- **F1 score** for the overall verdict prediction
- **Calibration** — are the model's confidence scores honest? Plot reliability diagrams. A well-calibrated model that says 80% confident is right 80% of the time.
- **Compare against base Gemma 4** — run the SAME test set through unfinetuned Gemma 4 to show the lift.

Document all numbers in `ml/eval/results.md`. These go directly into the Kaggle writeup. **Numbers that show no improvement disqualify the fine-tune from the Unsloth prize** — be ready to iterate if Round 1 shows weak gains.

### 6.5 — Publishing the LoRA adapter

When evaluation passes:

```
🧑 HUMAN ACTION REQUIRED
What you need to do:
  1. In the Kaggle notebook, ensure the LoRA adapter is saved (look for files in /kaggle/working/lora_adapter)
  2. From the notebook, run: model.push_to_hub("<your-hf-username>/satya-gemma4-e4b-lora")
  3. Confirm the upload succeeded at https://huggingface.co/<your-hf-username>/satya-gemma4-e4b-lora
  4. Add a model card (README.md on HF) describing: base model, training data, evaluation numbers, intended use, limitations
What you need to give me back:
  - The public Hugging Face URL of the published adapter
  - Confirmation the model card is filled in
Reason this is needed:
  Hackathon Unsloth Special Tech Prize REQUIRES published fine-tuned weights with benchmarks. No publication = no prize eligibility.
```

### 6.6 — Loading the LoRA adapter in the app

The fine-tuned weights are merged into the base model and converted to MediaPipe's `.task` format for on-device deployment. This is a multi-step process:

1. In the notebook: merge LoRA into base model → save as full Gemma 4 weights
2. Convert merged model to MediaPipe `.task` format using Google AI Edge's conversion tool (https://ai.google.dev/edge/mediapipe/solutions/genai/llm_inference/android#convert_model)
3. Upload the converted `.task` file to a separate Hugging Face repository (it's binary, large, must be hosted somewhere)
4. The app's model download logic (from Phase 1) is updated to download the fine-tuned `.task` file instead of base

This conversion sometimes fails for new model architectures. If it does, fall back to:
- Option A: ship base Gemma 4 in the app, run fine-tuned model only on the Kaggle-hosted demo flow
- Option B: keep the fine-tune in the writeup as a published research artifact (still wins Unsloth prize), use base Gemma 4 in the app

The agent chooses Option A if conversion fails, and clearly explains the choice in the writeup.

## 7. Track C — The Android App UI

### 7.1 — Visual identity

SATYA's visual tone: calm, serious, trustworthy. The opposite of social media — this is a tool you use when you're about to do something consequential.

| Property | Choice |
|---|---|
| Primary color | Deep indigo `#1A1F3A` |
| Accent — caution | Amber `#F59E0B` |
| Accent — verified safe | Sage green `#10B981` |
| Accent — danger | Muted red `#DC2626` |
| Background | Off-white `#FAFAF9` (light), near-black `#0A0A0A` (dark) |
| Font headings | Fraunces (serif, conveys seriousness) via `google_fonts` |
| Font body | Inter (clean, readable) via `google_fonts` |
| Icon style | Solid weight, Phosphor Icons via `phosphor_flutter` |

Avoid: gradients, emoji-heavy UI, playful illustrations. This is not a fun app.

### 7.2 — Screens

**Screen 1 — Home (`ui/screens/home_screen.dart`)**

The app's main surface when opened normally (not via share intent). Contains:

- App name and tagline in headline serif
- One primary action button: "Analyze from gallery"
- One secondary action: "Paste text or link"
- A subtle hint at the bottom: "Or share content directly to SATYA from any app"
- Footer link to "Verdict cache" (Phase 3 — shows recent community verdicts)

No bottom navigation. No tabs. One screen, one purpose.

**Screen 2 — Analyzing (`ui/screens/analyzing_screen.dart`)**

Shown while Gemma 4 is running. Contains:

- Subtle animation (not a spinner — something purposeful like a wave or scanning effect)
- Status text that updates as steps complete: "Extracting frames..." → "Analyzing audio..." → "Reasoning..." → "Finalizing verdict..."
- A subtle "running locally on your device" reassurance with a small lock icon
- Estimated time remaining (use rolling average of past analyses)

This screen is on display for 10–15 seconds. It carries emotional weight — make it feel deliberate.

**Screen 3 — Verdict (`ui/screens/verdict_screen.dart`)**

Where it all pays off. Layout (top to bottom):

1. **Verdict badge** — large, color-coded, the headline verdict ("LIKELY SYNTHETIC" in muted red, etc.)
2. **Overall confidence** — a horizontal confidence bar with the percentage and a calibration note
3. **Recommendation card** — one-line action ("Do not forward this content") with the corresponding color
4. **Evidence list** — collapsible card per piece of evidence: type, location in the content, plain-language description
5. **Explanation** — the model's two-sentence reasoning, with a "Tell me more" expander for the detailed explanation
6. **Action row** — three buttons: "Share verdict" (Phase 3), "Report incorrect verdict" (sends feedback to a Firebase collection), "Analyze another"

The verdict card design is your most-screenshot-able asset. Make it look good. Mock it in Figma first if anyone on the team can do that.

### 7.3 — Share intent integration

Setting up Android's share intent so SATYA appears in WhatsApp's "Share to" menu:

- The intent filter is already in `AndroidManifest.xml` from Phase 1
- Use `receive_sharing_intent` package to capture incoming shares in Dart
- Initialize the listener in `main.dart` so it works whether the app is cold-started by a share or already running
- When a share arrives, skip the home screen and navigate directly to the analyzing screen with the shared content

Test this manually: from WhatsApp, tap a video → Share → SATYA should appear in the list → tapping it should launch the app with the video pre-loaded.

### 7.4 — Media input handling

The home screen's "Analyze from gallery" button uses `image_picker` for images and videos, and a file picker for audio. Handle all three:

- Image: passed directly to the analysis pipeline
- Video: capped at 60 seconds (longer videos timeout reliably; show a warning if user picks a longer one)
- Audio: capped at 60 seconds same reason
- Text/URL: a dedicated text input field — for forwarded message text or URLs to suspicious content

### 7.5 — Error and edge case handling

The app must handle gracefully:

- Shared content is in a format we don't support → friendly error, suggest screenshot
- File is too large → offer to analyze first 30 seconds
- Model isn't initialized yet (cold start race condition) → wait with a brief loader
- Analysis returns `INCONCLUSIVE` → render it honestly, don't fake confidence
- User cancels mid-analysis → cleanly cancel the inference, free GPU memory

### 7.6 — Accessibility — non-optional

GemmaVision won partly because of how seriously it took accessibility. SATYA isn't built for blind users specifically, but accessibility increases who can use it:

- Every interactive element has a semantic label that TalkBack reads correctly
- Color is never the only way information is conveyed (verdict colors are always paired with text labels and icons)
- Font sizes respect system font scaling
- Sufficient contrast on all text (WCAG AA minimum)
- All animations respect "Reduce motion" system setting

### 7.7 — Theming

Support both light and dark mode from day one — Indian users often have system in dark mode, judges in light. Follow Material 3 theming via `ThemeData` and `useMaterial3: true`. Define the two themes in `mobile/lib/config/app_theme.dart`.

## 11. Common Failure Modes — Phase 2 Edition

| Symptom | Likely cause | Fix |
|---|---|---|
| Fine-tune doesn't improve over base | Dataset quality issues — too synthetic, too monocultural | Audit dataset, add regional examples, clean labels |
| Model produces free text instead of function call | Tool definition wrong or model needs more examples in dataset | Add at least 100 function-call examples in training data |
| Inference crashes the app | GPU OOM on lower-end phones | Drop frame count from 8 to 5; reduce image resolution to 512 |
| Verdicts wildly inconsistent between runs | Temperature too high | Lower to 0.2; set a fixed seed for reproducibility |
| Verdicts always confident-wrong | Model not calibrated; needs more "INCONCLUSIVE" training examples | Add explicit ambiguous examples to dataset |
| App freezes during analysis | Inference running on main thread | Move to isolate with `compute()` or `Isolate.spawn` |
| Share intent doesn't appear in WhatsApp | Manifest configuration | Re-verify Section 4.3 of Phase 1 |
| Frames extracted are all black | `ffmpeg_kit_flutter` permissions or codec issue | Check file accessibility, log ffmpeg output |
| Verdict screen renders blank | JSON parse error silently caught | Add explicit error UI with raw model output for debugging |

## 13. Mid-Phase Reality Check

Halfway through Phase 2 (end of Day 4), pause and answer honestly:

- Is the analysis pipeline producing verdicts that feel right on real content? If verdicts are nonsense, fine-tuning won't save you — debug prompts and schema first.
- Is the fine-tune actually learning anything? If validation loss is flat after 2 epochs, dataset is the problem, not training.
- Does the UI look like a real product or like a hackathon prototype? If the latter, allocate Day 5 to polish before integration.
- Have all team members run the app on their own devices? If only one person has touched the app, you have a single-developer risk.

If three or more of these are red, slow down Day 5 to fix before Day 6. A great Phase 2 is the difference between a winning submission and a forgettable one.
